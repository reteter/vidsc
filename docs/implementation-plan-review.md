# vidsc implementation plan: independent review

Review date: 14 October 2026. Reviewed documents: [implementation plan](implementation-plan.md) and [architecture research](research/2026-10-14-video-architecture.md).

This review evaluates the plan rather than an implemented application. All plan line references below were checked against the 309-line document present during review. The original plan and research were not edited. Technical observations were checked against the upstream sources linked beside them; moving branches and documentation must still be reconciled with the versions selected in M0.

## Overall assessment

**Proceed with M0/M1, but revise the media correctness gates before committing to the complete release.** .NET 10/WPF/Flyleaf is a plausible Windows stack. The separation of playback-native libraries from CLI tools, rational source timestamps, bounded derived caches, temporary exports and explicit track choices is appropriate. Three projects, JSON persistence and one initial background job are proportionate to this application.

The main weakness is that the plan describes the desired results of smart rendering, precise navigation and validation more completely than the mechanism for proving them. The supplied x265 Main10/open-GOP file is a genuine feasibility gate, not routine FFmpeg plumbing. Software encoding is a useful reference, but does not itself establish compatible splicing. No source reviewed here proves universal compatibility between arbitrary x265, NVIDIA HEVC and newly encoded boundary regions.

There is no identified P0 emergency in an unimplemented application. The two P1 findings below require explicit contracts before the relevant feature can be accepted; they do not block building the first playback prototype. M1 and M4 already contain the right high-risk investigation gates. Most remaining findings strengthen their evidence or specify work within an existing milestone, rather than identify a missing feature. P2 findings should be resolved in the indicated milestones. P3 changes are optional refinements.

## Findings

### R1 — P1: smart-render feasibility is underspecified

**Plan references:** lines 17, 25, 38; 180–193; risk response at line 298.

**Problem and consequence.** The research correctly warns against naive concatenation; the plan avoids assuming that NVENC will splice successfully and requires ten-bit preservation. M4 is already an early feasibility gate. However, “resolve compatible splice points” names the hardest result without defining the gate's compatibility deliverable. Matching codec/profile, bit depth and dimensions is insufficient to specify handling of parameter-set IDs, VPS/SPS/PPS changes, sample-entry configuration, reference-picture state, leading pictures and reorder delay. “Use compatible tested reference encoding” is not a guaranteed remedy for x265/NVENC incompatibility. Without a bounded supported-source matrix and a decision point, M4 can become an indefinite codec-engine project that prevents the complete release.

**Evidence.** FFmpeg's concat demuxer requires compatible streams/time bases and can produce timing gaps; it does not supply this codec-specific proof. NVIDIA exposes sequence parameters generated by the configured encode session. These facts support a compatibility investigation, not a claim that source and boundary parameters must always be byte-identical or that different parameter sets can never coexist. [FFmpeg concat documentation](https://ffmpeg.org/ffmpeg-formats.html#concat), [NVENC sequence-parameter handling](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/nvenc-video-encoder-api-prog-guide/index.html#retrieving-sequence-parameters).

The referenced smartcut code has HEVC-specific encoder-option recovery, header handling and timestamp repair. Its repository also states that public development stopped. That is implementation evidence of the engineering burden, not a reusable correctness guarantee. [smartcut video cutter](https://github.com/skeskinen/smartcut/blob/main/smartcut/video_cutter.py), [smartcut maintenance status](https://github.com/skeskinen/smartcut#video-smartcut).

**Recommended change.** Split M4 into feasibility and production work. The feasibility output should be a codec/container compatibility table, an explicit choice of bitstream/muxing implementation, independently decodable copy-region rules, parameter-set/configuration handling, timestamp reconstruction rules and supported/unsupported results for both supplied sources. State whether `hev1`/`hvc1` and `avc1`/`avc3` behavior is relevant to the selected implementation; do not choose tags solely by renaming metadata. Add a boundary quality policy separately from frame accuracy. Keep NVENC as a measured follow-on encoder choice.

**Risk closure.** Pass short labeled H.264 and HEVC Main10 tests with both joins, copied-interior evidence and independent decode, then several cuts on the supplied x265 file and at least one NVIDIA HEVC sample. Record which cases remain unsupported. If the required corpus fails, make an explicit architecture/scope decision before production M4; do not count a full transcode or a disabled required feature as success. A usable strict-copy intermediate release can still be delivered while this decision is resolved.

### R2 — P1: the frame-selection and output-time contract is incomplete

**Plan references:** lines 93–99, 105–108, 147–148, 158, 170–175, 188–191.

**Problem and consequence.** Integer rational timestamps and `[start, end)` are good foundations, but do not answer what happens when a requested time falls inside a displayed frame. Nor do they define whether an Out command includes the frame currently visible, how the terminal frame duration is represented, how duplicate/missing timestamps are handled, or how source PTS maps to the completed output. Two workers could therefore produce different “exact” retained sequences while each believes it obeys the document. PTS and DTS should remain distinct, but missing DTS in the inspector does not remove the need for a valid output decode timeline.

**Recommended change.** Define a presentation-frame boundary resolution rule and record the resolved frame identity/time separately from the requested time. Specify In/Out keyboard behavior, rounding in each rescale, EOF treatment, common stream epoch and the output/source mapping. Include frame/packet duration and discontinuity handling in the descriptor/planner contract where needed. If timestamps are not trustworthy enough, expose the limitation or reject exact mode. Do not fix uncertain decode timestamps by arbitrary increments without proving presentation timing remains correct.

**Risk closure.** Use fixtures with fractional 24000/1001 timestamps, VFR intervals of visibly different duration, nonzero/negative starts, audio offsets and edit lists. Requests immediately before/at/after a frame boundary must produce one documented retained-frame sequence. The exported first PTS, last PTS **and last presentation end** must match that sequence, with the documented rescale tolerance. Check the source/output mapping after save/reopen, not only inside one worker invocation.

### R3 — P2: Flyleaf timing APIs need a stricter acceptance test

**Plan references:** lines 96, 99, 147–153; line 296.

**Problem and consequence.** M1 already warns against assuming accuracy, but the conditional “if Flyleaf exposes only coarse time” understates a specific integration trap. The upstream `CurTime` contract includes a user's pending seek time, and setting it converts ticks to integer milliseconds. `SeekAccurate(int ms)` documents half-frame-distance accuracy. The seek completion event passes the requested milliseconds in the inspected path. Consequently, binding editor In/Out to `CurTime`, or treating `SeekCompleted` as observed frame PTS, can select a neighboring frame or stale request while reporting success. This does not prove Flyleaf cannot meet the requirement. [Flyleaf Player time property](https://github.com/SuRGeoNix/Flyleaf/blob/master/FlyleafLib/MediaPlayer/Player.cs), [Flyleaf seek implementation](https://github.com/SuRGeoNix/Flyleaf/blob/master/FlyleafLib/MediaPlayer/Player.Playback.cs).

**Recommended change.** Make M1 explicitly prove the path from a seek/step request to the frame actually presented. The adapter should distinguish requested target, pending generation, completion and observed frame identity/time. Document which pinned Flyleaf API or narrow integration hook supplies the observation. Keep the desired slider position separate from the confirmed edit position. Inspect callback threading/reentrancy before forwarding player operations from event handlers.

**Risk closure.** On labeled CFR and VFR fixtures, verify the displayed frame visually or through a trustworthy presentation hook and compare it with the source frame map. Include sub-millisecond fractional frame times, backward stepping, many coalesced requests and a source switch during a pending seek. A completion event containing the requested time is insufficient. Confirm the behavior against the pinned version; the reviewed master source is not a release-version guarantee.

### R4 — P2: define validation oracles and assurance levels

**Plan references:** lines 175–178, 191, 243, 265–290.

**Problem and consequence.** The plan usefully says that error-free decoding alone is insufficient, but “known frame identities,” “matching encoded payloads” and “requested representation” are not yet executable oracles. Lossy boundary re-encoding cannot generally pass exact source pixel hashes. Conversely, copied compressed bytes do not prove identical reconstruction if the copied region still depends on different re-encoded reference pictures. Boundary neighborhoods at the clip start/end also do not automatically cover the two internal smart-render joins. A file can decode with concealment and still violate the intended retained sequence.

**Recommended change.** Define separate assertions: robust synthetic frame labels for sequence; normalized elementary payload comparison for copied data; decoded source/output comparison for regions expected to reconstruct identically; metadata/bit-depth checks; a separately chosen boundary-quality criterion; and exact rational timing checks. State normalization when bitstream filters alter framing or headers. Decode each exported short fixture fully from a fresh decoder, and check both internal joins. Select at least one external target playback path for MP4 compatibility rather than validating only with the library that assembled it.

**Risk closure.** A deliberate omitted/duplicated frame, wrong reference, eight-bit boundary, bad last-frame duration and A/V shift must each fail the appropriate test. Lossy yet correct boundary frames must pass sequence tests without requiring pixel identity. Document production validation as a limited boundary/structure check unless it actually scans the whole export; do not label every committed long output “fully validated.”

### R5 — P2: coverage and safety must not be inferred from a probe request

**Plan references:** lines 96, 157–166, 170–171.

**Problem and consequence.** Progressive windows and overlap deduplication are sensible, but “covered-interval metadata” has no completeness rule. ffprobe can seek earlier than requested, and a relative duration is measured from the actual seek result. A request for `120%+10` might not inspect the intended interval up to 130 seconds. Packet PTS is also not necessarily ordered by encounter. Filling the requested coverage range or using only its maximum PTS can therefore hide uninspected candidate/dependency regions. [ffprobe interval semantics](https://ffmpeg.org/ffprobe.html#Main-options).

**Recommended change.** Specify actual observed scan coverage, incomplete/unknown regions, continuation behavior and the evidence required to classify a start/end as safe. Keep packet/index availability distinct from codec/dependency verification. Around a proposed export, require enough preceding and following context for the selected policy; do not mark a CRA safe merely because its NAL type was recognized. Handle absent packet positions in the deduplication identity.

**Risk closure.** A long-GOP fixture with seeks that land early must leave real holes visibly incomplete and trigger additional reads. Compare the progressive result with an exhaustive small-fixture reference. Include overlapping windows, B-frame PTS reordering, missing DTS/position, CRA with leading pictures and cancellation before coverage completes. No unknown area may become a verified export boundary.

### R6 — P2: audio precision needs a reproducible policy

**Plan references:** lines 40, 47, 99, 105, 178, 188–191, 299.

**Problem and consequence.** Preserving 5.1 and disclosing packet precision are correct. They do not specify which packets are retained when a requested video boundary intersects an audio packet, what timestamp is used as the shared output origin, or what deviation fails validation. AAC priming/edit-list behavior also cannot be reduced to “one packet” in every source. A vague measured-offset check can accept a systematically shifted clip.

**Recommended change.** Choose and document start/end packet inclusion rules, the output origin and treatment of priming/skip information for copied AAC and AC-3. Report measured leading/trailing deviation per selected track. Distinguish an allowed edge extension from a newly introduced A/V offset or cumulative drift. Keep sample-exact audio outside the default until explicitly added; avoid implying that disclosure permits arbitrary timing damage.

**Risk closure.** Use impulse/tone fixtures with known A/V alignment, delayed and multiple audio tracks, AAC priming and AC-3 packets crossing both boundaries. Assert the chosen retained audio intervals and stable relative alignment near the start, middle and end. Derive tolerances from the defined policy and fixture, rather than inventing a universal 20/32 ms guarantee.

### R7 — P2: scene timing and worker packaging need an early smoke gate

**Plan references:** lines 34, 100–101, 137, 210–218, 237–243.

**Problem and consequence.** The plan selects PyAV and requires source-time mapping, but does not specify whether imported results are original source PTS, normalized backend positions or rounded CSV seconds. Interval analysis adds another origin. Worker caches also need backend, scale/color treatment and stream selection in addition to detector/version/parameters. A correct VFR-aware backend does not guarantee that every exported frame-number format is exact.

**Evidence.** PySceneDetect's backend documentation distinguishes approximate VFR frame numbers from accurate position timing. Release 0.7.2 warns that `save-keyframes` frame numbers are approximate for VFR, and explicitly announces PyAV 19 and FFmpeg 9 in its Windows distribution. Thus the chosen packaged route is plausible; missing PyAV should not be assumed as a factual blocker. [PySceneDetect backend timing](https://www.scenedetect.com/docs/latest/api/backends.html), [PySceneDetect 0.7.2 release](https://github.com/Breakthrough/PySceneDetect/releases/tag/v0.7.2).

**Recommended change.** Run one tiny pinned Windows-worker analysis in M0/M2, and record its actual command/output schema. Define origin, precision, stream selection, interval offsets and result ownership in a small worker protocol. Prefer source-linked time values over nominal-FPS frame counts. Include backend/build, scale, color policy and source identity in cache keys. GPU `scdet` results and PySceneDetect adaptive results need separately named algorithm contracts; one is not automatically an accelerated implementation of the other.

**Risk closure.** Known transitions in nonzero-start, VFR and interval-only fixtures map to the same source frames. Repeating CPU/GPU/proxy analysis records both timing correctness and differences in detection behavior. Packaged execution, cancellation and corrupt-output handling must pass without development Python or FFmpeg on PATH.

### R8 — P2: define how running work yields to interaction

**Plan references:** lines 44, 101, 159, 173, 203, 216, 222–231, 300.

**Problem and consequence.** One queued analysis job and bounded channels prevent uncontrolled application queues, but do not bound a running FFmpeg/PyAV process's decoder threads, GPU use or reads. Lower queue priority cannot preempt that process. Thumbnail and export work can also overlap with “one analysis job.” A single scan on a mechanical source disk can disrupt exact seeks. Leaving actual contention control to M7 risks building M2/M6 around an ineffective priority promise.

**Recommended change.** Start with simple explicit limits in M2: enumerate all job classes sharing source/storage/GPU resources, cap their concurrency and thread settings where supported, cancel obsolete visible work and make background analysis opt-in. Choose a supported interruption strategy such as bounded windows with checkpoints or cancellation/restart; do not rely on undocumented process suspension. Handle stalled workers with a recorded failure/cancellation deadline. Avoid a generic scheduling framework.

**Risk closure.** Measure playback and randomized seeks with indexing, scene detection and export separately active. Record contention and verify cancellation actually releases the resources. On the user's intended storage, a permitted background configuration must preserve the agreed interaction target. If not, transparently serialize or stop that job while navigating.

### R9 — P2: close output-transaction and source-identity gaps

**Plan references:** lines 43, 94, 111, 114, 173–178, 201, 229, 259.

**Problem and consequence.** The safety intentions are good, but a one-time source recheck and an early naming-conflict check do not establish safety through a potentially long export. The sampled fingerprint is an identity hint rather than proof of all source contents. The plan also does not define what happens if the destination appears after the initial check, validation fails, the process crashes between finalization and promotion, or a sidecar export is only partially completed.

**Recommended change.** Define a minimal owned-output transaction: source/destination identity checks, exclusive temporary ownership, no-clobber promotion unless the user selected replacement, late conflict resolution and a commit/result record. Recheck the source after reading or use an appropriate read-sharing policy; explain its limitations. Treat file identity/path aliases when rejecting a source as destination. Keep bounded failed-output diagnostics and an intentional quarantine/delete policy. Sidecar sets need an explicit partial-success state. Add a small autosave/recovery rule; atomic manual saves alone do not provide session recovery.

**Risk closure.** Tests create a destination conflict after export begins, modify the source during reading, fail validation and simulate interruption before/after promotion. Existing source/completed-output bytes remain unchanged, no unrelated temporary file is removed, and restart identifies only the app's own recoverable artifacts. These are targeted tests, not grounds for new infrastructure.

### R10 — P2: specify the early packaging experiment and license decision

**Plan references:** lines 32–34, 47, 136–141, 235–245, 301, 307.

**Problem and consequence.** The early packaging checkpoint is valuable, but has no enumerated runtime set or pass criterion. Flyleaf native loading, separately invoked FFmpeg/ffprobe and the scene worker are different lookup problems. A successful single-file WPF shell does not resolve the worker layout. The requirement to include notices also does not by itself complete distribution obligations for each actual binary/build.

**Evidence.** .NET documentation distinguishes managed bundling, native-library extraction and APIs whose paths change in a single-file deployment. Its current documentation marks `IncludeAllContentForSelfExtract` as a compatibility mode that is not recommended, so embedding every worker through that setting should not be an assumed long-term packaging strategy. FFmpeg's license guidance ties obligations to configured components/builds. [Microsoft single-file deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview), [FFmpeg license guidance](https://ffmpeg.org/legal.html).

**Recommended change.** Keep the framework-dependent choice if it suits local use; explicitly require the x64 .NET 10 Desktop Runtime and minimum supported Windows version in delivery checks. Test a publication containing the actual Flyleaf native set, one CLI probe/export and one scene job in M0/M1. Record exact worker directories, extraction behavior, writable cache paths and bundled dependencies. Decide personal-use versus redistribution before choosing the production encoder/tool builds; for redistribution, record required source/build/replacement information as applicable, not only license names. Prefer a documented standard runtime-folder layout if a single EXE cannot support the tested set.

**Risk closure.** Run the publication outside the repository with development paths removed, in a spaced/Unicode path, with fresh extraction state and no development Python. Prove child tools use the pinned bundle. A missing .NET Desktop Runtime must give an actionable prerequisite outcome. Review the delivered manifest against actual files/configurations before M8. This is a packaging requirement, not a legal conclusion that all GPL subprocesses determine the application license.

### R11 — P2: clarify the usable-editor milestone and resist optional scope expansion

**Plan references:** lines 11–25, 124–130, 193, 206, 210–218, 307–309.

**Problem and consequence.** The plan says a usable stream-copy editor is an intermediate milestone, while M5's acceptance workflow requires either supported mode and M4 precedes it. It is unclear whether M5 can be accepted while M4 still has feasibility work. The complete release also includes several navigation/analysis tools, and black/silence markers appear as additional M6 work without being part of the first-release list. This ambiguity can delay the core useful application or turn optional analysis into accidental blockers.

**Recommended change.** Define M5a as the explicitly usable strict-copy workflow after M1–M3. Keep an early small M4 feasibility spike, then integrate proven accurate cutting as M5b/production M4. Full completion must still include the confirmed accurate-cut capability on the defined corpus; this is not a request to remove it. Keep scene detection, sparse thumbnails and basic waveform in the declared release. Move black/silence/freeze detectors, custom GPU metrics and extra encoder paths to measured follow-on work unless explicitly selected as required.

**Risk closure.** Each milestone has one unambiguous acceptance workflow and a supported capability list. A user can navigate, persist and export useful strict-copy ranges without waiting for all smart-render production work. The final milestone cannot pass by merely hiding accurate cut. Optional tools have no hidden dependency on its completion.

### R12 — P2: make performance and lifecycle gates repeatable

**Plan references:** lines 45, 149–153, 223–231, 257, 278–290.

**Problem and consequence.** Targets are appropriately provisional, but “representative sustained session,” “without accumulating resources,” “returns toward baseline” and “no sustained growth” lack durations, repetitions or accounting boundaries. A 2–4 GiB target could mean UI private memory only while a native/Python child consumes additional gigabytes. Current VRAM budget and process allocations are also distinct. CPU/storage are unknown, so the seek targets cannot yet be a credible release gate.

**Recommended change.** Define named scenarios and a machine baseline in M1: supplied sources, fixed/seeded seek positions, cold/warm state, playback duration, source-switch/cancel counts and one competing job. Measure UI responsiveness, actual frame identity, seek median/p95, drops, A/V drift, total app-owned process commit/private memory, handles/process count and relevant GPU usage separately. State whether the RAM target is a soft normal target or an enforced upper budget; bound cache allocations independently. Choose performance pass/fail thresholds after measuring the intended storage and CPU.

**Risk closure.** The same benchmark scenario can be repeated after a change and compared with prior evidence. A resource leak or regression fails a declared criterion. The final report includes child-process memory and exceptions for long-GOP exact seeks, and does not confuse OS file cache with retained application frame memory.

### P3 refinements

- **Capability presentation (lines 21, 42, 95, 172, 241):** use a compact per-file result with playback, strict-copy and accurate-cut support plus reasons. Avoid spreading eligibility logic through views or building a generic plugin capability framework.
- **Optional JSON evolution (line 114):** choose a simple policy for older schemas when one actually exists. Future-schema rejection is already appropriate; do not implement a migration framework for version one.
- **Minor wording (lines 99, 191, 290):** distinguish the last frame's PTS from its presentation end, “same representation” from “same quality,” and boundary validation from whole-file validation. These edits should follow the concrete contracts in R2/R4.

## Proposed milestone corrections

| Milestone | Concrete adjustment | Evidence to retain |
| --- | --- | --- |
| M0 | Pin compatible runtime sets; choose personal-use/redistribution intent; publish the actual native/CLI set; run one tiny scene worker job | Manifest, artifact layout, command/schema and clean-path smoke result |
| M1 | Prove observed displayed-frame timing and callback ownership before binding edit boundaries; establish one repeatable performance baseline | Labeled CFR/VFR seek/step results, lifecycle counts and actual GPU path |
| M2 | Define frame resolution/time mapping and truthful progressive coverage; implement minimal contention/cancellation limits | Small exhaustive-reference index comparison, offsets/edit-list cases and visible incomplete coverage |
| M3 | Fix audio selection, output transaction and validation tiers; validate strict-copy CRA behavior | Fully decoded synthetic exports, normalized payload evidence, track timing and failure tests |
| M4a | Focused smart-render feasibility on H.264 and supplied HEVC Main10/open-GOP; no broad production worker yet | Compatibility matrix, both joins, source/output mapping and explicit go/no-go decision |
| M5a | Deliver the usable strict-copy editor after M1–M3, using the evolving shell | Open/edit/save/reopen/export workflow with requested/effective boundaries |
| M4b / M5b | Implement and integrate accurate cut only for the proven corpus; assess NVENC separately | Exact retained-frame sequence, copied interior, ten-bit metadata and audio policy |
| M6 | Complete scene/thumbnail/waveform tools under the tested worker-time contract; make optional detectors explicit follow-ons | Source-aligned results, cache invalidation and contention/cancellation checks |
| M7 | Tune from measured user storage/CPU rather than adding large caches preemptively | Repeatable cold/warm metrics including child processes and GPU budgets |
| M8 | Re-run the complete delivered workflow with actual tools, prerequisites and both supported export modes | Clean-location results, capability documentation and distribution manifest |

This sequence retains the original technology choices and required accurate-cut mode. It makes the expensive unknowns visible early while giving the user a useful strict-copy editor before the final smart-render integration is complete.

## Verification performed and remaining uncertainty

Performed: read both local documents; checked the plan's exact line numbers; compared requirements, milestone dependencies and corpus; consulted primary upstream documentation/source for Flyleaf seek timing, FFmpeg concat/probe behavior, NVENC parameters, x265 open-GOP, smartcut maintenance/implementation, PySceneDetect VFR/packaging and .NET single-file deployment. The sandbox checklist confirmed `rg`, `jq` and `pandoc` access. After writing, the review's line references, local links, heading structure and text encoding were checked.

Not performed: application build, Flyleaf UI prototype, new GPU benchmarks, actual source/export operations, smart-render splice experiments, portable worker execution or license compliance determination. Existing research smoke tests remain evidence only for the intervals and tools it records. None of the recommendations above should be interpreted as a measured runtime failure or a guarantee that the required smart-render corpus will pass.
